# ZhiYing 关系后处理 V2 重构方案

> 日期：2026-09-12  
> 状态：已评审，Phase 0 / Phase 1 已完成；可进入 Phase 2 实施
> 范围：人物身份归并、关系语义归一化、证据验证、默认展示收敛、异常修复、单章重跑一致性
> 核心原则：**程序负责准备有限问题，模型负责有限判断；账本尽量完整，默认关系图只展示最有价值的信息。**

---

## 0. 产品目标先于算法

本次重构不以“构建最严格的知识图谱”为目标，而以 ZhiYing 的实际用户目标为准：

> **用户把一本自己尚未读完、甚至基本没读过的书交给系统，系统应尽量自动生成一张完整、可信、重点清晰的人物关系图。**

因此，本次重构采用以下产品取舍。

### 0.1 完整性优先，但不能把不确定内容伪装成事实

目标不是“宁可漏掉也绝不犯错”，而是：

- 主要人物尽量不漏；
- 主要关系尽量不漏；
- 不确定信息继续自动处理，而不是立刻丢给用户；
- 最终仍无法确认的内容可以留在内部 `pending/unresolved`，但不能凭空变成 `confirmed`；
- 默认关系图不应被大量低价值或低置信度边淹没。

### 0.2 用户不是校对员

目标用户通常没有读过这本书，因此不能把以下任务当作正常产品流程：

- 让用户判断两个名字是不是同一个人；
- 让用户逐条处理 pending relation；
- 让用户选择几十个关系冲突；
- 让用户理解内部 predicate / relation registry；
- 每次分析后要求用户人工收尾才能得到可用图。

人工编辑继续保留，作为高级用户纠错能力，而不是系统正常完成分析的必要条件。

### 0.3 人物自动合并是核心能力，不是可选附加项

“同一个人物裂成多个节点”会直接破坏整张图，因此身份解析必须自动完成绝大多数工作。

原则：

- 先用确定性规则找候选；
- 对真正有歧义的 identity component 进行一次批量模型判断；
- 模型不能自由翻书调查；
- 信息不足时允许保留两个节点，但不要求普通用户介入；
- 错误合并仍然比暂时未合并更严重，因此所有 merge 必须经过服务端结构校验。

### 0.4 关系采用“半开放 registry”

不是完全自由生成，也不是死枚举。

采用：

```text
常见关系 seed registry
+ 全书级已有 learned registry
+ 必要时新增语义类型
```

即：

> **常见关系尽量直接归一；罕见但重要的文学关系允许新增。**

### 0.5 “事实保留”与“默认展示”分离

这是 V2 必须明确的产品原则。

例如：

```text
A 与 B：朋友 + 师徒
```

账本可以同时保留：

```text
friend_of
mentor_of
```

但默认图只需要显示：

```text
师徒
```

“朋友”进入详情里的“更多关系”，而不是被删除。

因此：

> **弱关系被强关系压制，是 Display Policy，不是事实冲突。**

这与 PRD 中“多标签 + 软硬展示”的原始设计保持一致。

### 0.6 不再默认运行“全书纠错总结 Agent”

旧设计把 Final Reconcile 当作每本书固定阶段。

V2 改为：

```text
正常情况：0 次 Final LLM

只有程序检测到少量、会明显污染最终图的高影响异常
→ ExceptionCase[]
→ 一次无工具批量判断
```

也就是说，**取消“先生成 suspects，再让 Agent 自己调查整本书”的产品概念。**

## 1. 当前问题的真正根因

目前性能问题不是《悉达多》太长，也不是几十条关系天然需要大量推理，而是旧架构把一个有限数据整理问题变成了多轮 Agent 调查。

### 1.1 pending 被错误提升成全书疑点

当前：

```python
detect_missing_evidence()
```

会把每一条：

```text
status == "pending"
```

直接变成一个 `MissingEvidence suspect`。

因此：

```text
22 suspects
```

很可能只代表：

```text
22 条还没被证据验证器确认的 occurrence
```

并不代表 22 个全书级错误。

V2 中：

```text
pending relation
→ 普通待判定状态
≠ relation conflict
≠ Final Reconcile case
```

### 1.2 相同语义按章节重复处理

当前虽然已经有 batch 和任务级 cache，但主要入口仍然是：

```text
for chapter:
    normalize_relations(chapter.relations)
```

这会让章节边界影响关系归一化。

V2 的单位改为：

```text
全书唯一 RelationSemanticCluster
```

### 1.3 Final Reconcile 是自由探索式 Tool Agent

现有模式：

```text
全书 prompt
→ LLM
→ 查工具
→ LLM
→ 再查工具
→ ...
→ submit_reconciliation
```

即使裁剪历史，它仍然具有以下问题：

- 调用次数不可自然预测；
- 模型可以不断扩大调查范围；
- 重复搬运相同 cast / ledger / chapter 信息；
- pending 越多，探索动力越强；
- 最终收益与成本不成比例。

这不是需要继续调 Prompt 的问题，而是执行模型不适合当前任务。

## 2. V2 总体架构

新的主路径：

```text
Chapter Agent 原始抽取
  ↓
CastWriter / rebuild_cast
  ↓
Identity Candidate Compiler
  ↓
Identity Resolver（仅歧义 component，0～N 有限批次）
  ↓
确定性应用人物 merge / alias
  ↓
Relation Preprocessor
  ↓
全书 Relation Cluster Compiler
  ↓
Semantic Resolver（只处理歧义 cluster）
  ↓
Evidence Resolver（局部窗口、全书收集、有限 batch）
  ↓
Canonical Fact Compiler
  ↓
Display Policy Compiler
  ↓
High-impact Anomaly Compiler
  ↓
是否存在真正需要语义修复的 ExceptionCase？
  ├─ 否 → 完成
  └─ 是 → Exception Resolver（无 tools，一次/有限 batch）
             ↓
           Validator
             ↓
           Patch Compiler / Applier
  ↓
事务性发布
```

与旧架构最大的区别：

> **不再存在一个“最后再读一遍全书，看看哪里不对”的模型。**

## 3. Identity Pipeline：自动认人优先

身份错误对关系图的破坏大于单条关系错误，因此 Identity Pipeline 应放在关系后处理之前。

### 3.1 Identity Candidate Compiler —— 确定性

输入：

- cast；
- 各章 `ChapterPerson`；
- canonical name；
- aliases；
- 来源章节；
- 必要的局部出现文本。

构建 identity candidate graph。

边来源包括：

- A canonical name == B alias；
- alias overlap；
- 标准化后名称一致；
- 同一章节/相邻章节中稳定称谓切换；
- 已有人工作为强覆盖。

但这里只生成候选，不直接因为字符串相似就合并。

#### 3.1.1 Candidate Edge 必须分级，泛称不能桥接 component

`connected component` 的召回很高，但也有一个危险：如果任何 alias overlap 都能连边，中文小说中的泛称 / 头衔会把大量无关人物串成一个巨型 component。

因此候选边至少分成两档：

```text
hard component edge
- canonical name == 对方明确 alias
- 规范化后专名完全一致
- 已有人工 merge / rename 约束
- 其他低歧义、可确定的身份等价规则

soft evidence edge
- 普通 alias overlap
- 同章 / 相邻章称谓切换
- 上下文中可能表示同人的线索
```

只有 `hard component edge` 可以直接参与 connected component 的连通性计算；`soft evidence edge` 只能作为 component / case 内的辅助证据，不能单独把两个 component 桥接起来。

以下高歧义词默认不得作为 component bridge：

```text
父亲 / 母亲 / 老爷 / 夫人 / 先生 / 师父 / 大人 / 少爷 / 小姐
以及其他多人可共享的角色词、敬称、职衔、泛称
```

实现上可以维护一份可配置的高歧义称谓表，也可以根据同一名称命中人数动态降权。原则只有一个：

> **宁可让信息不足的两个人暂时分开，也不能因为共享泛称把多个真实人物错误合并到同一 identity component。**

### 3.2 用连通分量替代人物两两 suspect

例如：

```text
A ↔ B
B ↔ C
A ↔ C
```

不生成 3 个问题。

改为：

```text
IdentityComponent {A, B, C}
```

一个 component 一次判断。

### 3.3 Identity Resolver —— 批量判断，不探索

建议数据结构：

```python
class IdentityCase:
    case_id: str
    person_ids: list[str]
    canonical_names: list[str]
    aliases: dict[str, list[str]]
    chapter_ids: list[int]
    evidence_snippets: list[str]
```

模型输出必须明确分组：

```python
class IdentityDecision:
    case_id: str
    groups: list[list[str]]
    canonical_keep_id: dict[str, str]
    alias_additions: dict[str, list[str]]
    unresolved_person_ids: list[str]
    reason: str
```

模型只能引用输入中的 person_id。

### 3.4 自动化策略

- 明确同人 → 自动 merge；
- 明确不同人 → 保持分离；
- 信息不足 → 保持分离，不要求普通用户处理；
- manual merge / rename 永远优先；
- merge 前必须验证不存在未知 ID、自环、环状 merge 和非法跨对象修改。

V2 不再把“待合并队列”作为普通用户必须完成的步骤。

### 3.5 防剧透：Identity 必须支持 chapter slice projection

PRD 把“只看到前 N 章”定义为一等公民。V2 的 Identity Pipeline 是全书级的，因此必须防止**后文身份信息反向污染前 N 章视图**。

典型泄漏包括：

```text
第 10 章才明确 A = B
→ 用户只看到第 5 章时，A/B 已被提前合并

第 9 章才出现某人的真实姓名
→ 第 3 章视图提前显示真实姓名 / 后期别名
```

因此所有自动 identity decision 必须保留来源与生效范围，至少包含：

```python
IdentityDecisionProvenance:
    evidence_chapter_ids: list[int]
    effective_from_chapter: int
```

第一版采用保守规则：

```text
effective_from_chapter = max(evidence_chapter_ids)
```

查询：

```text
GET graph?to_chapter=N
```

时，只允许应用 `effective_from_chapter <= N` 的自动 merge / alias decision。若某个全书 identity decision 使用了后文证据，即使它对全书视图是正确的，也不能回填到更早切片。

人工 merge / rename 属于用户主动纠错，可作为显式强覆盖应用；自动流程不得把后文发现伪装成前文已知事实。

原则：

> **防剧透优先于早期切片里的身份合并完整度。宁可前 N 章暂时裂成两个点，也不能用 N 章之后的信息提前认人。**

## 4. Relation Preprocessor —— 完全确定性

输入：所有已完成章节的原始关系 occurrence。

### 4.0 Raw / Derived SSOT 边界必须固定

V2 必须把原始抽取与后处理派生产物彻底分开：

```text
extraction/*
= Chapter Agent 原始输出
= immutable raw snapshot
= 后处理唯一输入 SSOT

ledger/* / canonical facts / display policy
= derived artifacts
= 可随 V2 generation 整体重建
= 绝不能成为下一代后处理的输入基线
```

每次完整 V2 postprocess、恢复任务、单章 rerun 后的全书 postprocess，都必须：

```text
1. 从所有有效 extraction snapshots 重新生成工作 ledger / cast
2. replay manual cast edits
3. 再运行 Identity / Relation / Evidence / Canonical / Display
```

禁止出现：

```text
上一代 postprocessed ledger
→ 作为下一代 Identity / Semantic / Evidence 的输入
```

否则旧 identity rewrite、旧 predicate、旧 verification status 会被下一代继承，形成不可审计的“二次加工事实”。

建议所有派生产物带：

```python
generation_id: str
source_snapshot_hash: str
```

用于诊断、缓存失效和幂等性测试，但 raw extraction snapshot 本身不因后处理被改写。

人工编辑也不写回 raw extraction，而是继续保存在独立 override / human edit 层，由每代重建时 replay。

职责：

1. quote 精确定位；
2. 标准化空白、全半角和无语义标点差异；
3. 无向关系人物对排序；
4. 校验 person_id；
5. 保留 `raw_relation`；
6. 生成稳定 occurrence / evidence hash；
7. 计算完整 descriptor fingerprint。

### 4.1 exact fingerprint 必须保守

安全 exact fingerprint 使用标准化后的完整 descriptor：

```python
RelationFingerprint = {
    "label": str,
    "category": str,
    "definition": str,
    "directed": bool,
    "subject_role": str,
    "object_role": str,
}
```

不能为了减少 cluster 数，在确定性阶段擅自通过模糊字符串相似度合并语义。

## 5. Relation Cluster Compiler —— 全书级处理

目标：

> 模型处理唯一语义簇，不处理每一条 occurrence。

建议结构：

```python
class RelationSemanticCluster:
    cluster_id: str
    member_relation_ids: list[str]
    representative: RelationDescriptor
    observed_labels: list[str]
    observed_raw_relations: list[str]
    chapter_ids: list[int]
    candidate_predicates: list[str]
```

流程：

```text
所有 occurrences
→ exact descriptor dedupe
→ registry alias / exact match
→ compatible candidate retrieval
→ unresolved semantic clusters
```

相同关系在 12 章出现 20 次：

```text
20 occurrences
→ 1 semantic cluster
→ 最多一次 semantic decision
→ 广播给 20 条 occurrence
```

## 6. Semantic Resolver —— 半开放关系类型

### 6.1 模型不读取完整 registry

每个 cluster 只携带：

- cluster descriptor；
- 代表性 raw descriptions；
- 有限 candidate predicates；
- cluster_id。

候选检索顺序：

1. 完整 descriptor exact；
2. alias exact；
3. label exact；
4. `category + directed + roles` 兼容过滤；
5. 必要时 lexical shortlist。

### 6.2 `new` 必须谨慎

如果 shortlist 召回漏掉已有等价 predicate，就会把 registry 再次拆碎。

因此：

- `existing` 只能引用提供的 predicate；
- `new` 只在服务端确认已检查兼容候选集合后允许；
- 模型不生成 predicate 主键；
- `new` 由服务端 `register()` 分配稳定 ID；
- 候选召回不足时应 `unresolved`，不能为了完成率强造新类型。

建议输出：

```python
class SemanticDecision:
    cluster_id: str
    action: Literal["existing", "new", "unresolved"]
    predicate: str | None
    reverse: bool
    reason: str
```

### 6.3 批处理

按 cluster 数和输入字符/token 双限制切 batch，不按章节切。

短篇正常目标：

```text
0～1 次 semantic request
```

硬上限可以按规模动态计算，而不是按章线性增长。

### 6.4 Registry 必须 generation-safe 且幂等

V2 会反复全书重建，尤其单章 rerun 后会重新跑 semantic pipeline。Registry 不能因此“越跑越肥”。

来源明确分层：

```text
seed     = 内置稳定定义
human    = 用户显式创建 / 修改的定义
learned  = 自动 semantic pipeline 学到的定义
```

约束：

1. `register()` 对完整 canonical descriptor 做确定性去重；
2. 自动 predicate ID 必须由稳定语义内容确定生成，不能使用随机 UUID；
3. 同一 descriptor 再次注册必须复用旧 predicate，不 bump registry version；
4. registry version 只在真实语义内容变化时增长；
5. `human` 定义优先于等价的 `learned` 定义，自动流程不得覆盖人工定义；
6. 每次 generation 开始时必须能明确区分“既有稳定定义”和“本代新 learned 定义”，便于失败回滚和诊断。

最低幂等验收：

```text
固定同一组 raw extraction snapshots
→ 连续运行 V2 两次
→ predicates / registry definitions / canonical fact ids / 默认图完全一致
```

模型输出可能存在随机性，但服务端不得因为同一语义重复运行而机械制造新的 predicate。

## 7. 初始关系类型：从 13 类扩展为“小而够用”的 seed registry

当前 seed registry 只有 13 类，且所有 `display_priority` 基本等价，不足以支持“强关系压制弱关系”的产品目标。

V2 建议给 `RelationDefinition` 增加：

```python
display_tier: Literal["hard", "mid", "soft"]
display_priority: int
```

必要时以后再增加：

```python
structural_constraints: ...
```

但第一版不要建立重量级 ontology。

### 7.1 建议的 seed 集合

以下是种子，不是合法值全集。

#### Hard —— 通常应成为默认图核心标签

亲属关系是人物图里最需要精确表达的一类。对中文小说尤其不能把“哥哥 / 弟弟 / 表兄 / 堂妹”全部压成“兄弟姐妹 / 堂表亲”。

因此 Hard seed 分成两层：

```text
精确常用亲属类型 —— 有明确原文时优先使用
宽泛 fallback 类型 —— 原文本身不够具体时才使用
```

##### A. 精确常用亲属类型

| predicate | label | 说明 |
|---|---|---|
| `husband_of` | 丈夫 | A 是 B 的丈夫 |
| `wife_of` | 妻子 | A 是 B 的妻子 |
| `father_of` | 父亲 | A 是 B 的生父 |
| `mother_of` | 母亲 | A 是 B 的生母 |
| `adoptive_father_of` | 养父 | A 是 B 的养父 |
| `adoptive_mother_of` | 养母 | A 是 B 的养母 |
| `older_brother_of` | 哥哥 | A 是 B 的年长男性手足 |
| `younger_brother_of` | 弟弟 | A 是 B 的年幼男性手足 |
| `older_sister_of` | 姐姐 | A 是 B 的年长女性手足 |
| `younger_sister_of` | 妹妹 | A 是 B 的年幼女性手足 |
| `paternal_grandfather_of` | 祖父 | A 是 B 的父系祖父 |
| `paternal_grandmother_of` | 祖母 | A 是 B 的父系祖母 |
| `maternal_grandfather_of` | 外祖父 | A 是 B 的母系祖父 |
| `maternal_grandmother_of` | 外祖母 | A 是 B 的母系祖母 |
| `elder_paternal_uncle_of` | 伯父 | A 是 B 父亲的哥哥 |
| `younger_paternal_uncle_of` | 叔父 | A 是 B 父亲的弟弟 |
| `paternal_aunt_of` | 姑姑 | A 是 B 父亲的姐妹 |
| `maternal_uncle_of` | 舅舅 | A 是 B 母亲的兄弟 |

| `lover_of` | 恋人 | 明确双向恋爱/情侣关系 |
| `mentor_of` | 师徒 | 明确师承 |

这里不要求把中文亲属称谓词典穷举完，但**高频且能显著帮助读者理解人物关系的称谓应直接进入 seed**。

##### B. 宽泛 fallback 亲属类型

| predicate | label | 使用条件 |
|---|---|---|
| `spouse_of` | 夫妻 | 明确是配偶，但无法或无需区分丈夫/妻子 |
| `parent_of` | 亲子 | 明确父母子女，但性别/角色信息不足 |
| `adoptive_parent_of` | 养亲 | 明确养育亲子，但信息不足以细分养父/养母 |
| `sibling_of` | 兄弟姐妹 | 明确手足，但无法确定年龄/性别角色 |
| `grandparent_of` | 祖孙 | 明确祖孙，但父系/母系或性别不明确 |
| `uncle_aunt_of` | 叔侄/舅甥等 | 明确隔一代近亲，但具体支系不明确 |
| `cousin_of` | 堂表亲 | 明确同辈堂表亲，但无法进一步判断堂/表、年龄或性别 |

**禁止把已有精确信息降级成 fallback。** 例如：

```text
原文明示“哥哥” → older_brother_of
不得为了复用 registry → sibling_of

原文明示“表弟” → younger_male_cousin_of
不得归一成 cousin_of
```

Semantic Resolver 的候选排序必须遵守：

```text
精确等价 > 精确常用 seed > 宽泛 fallback
```

只有原文证据本身不够具体时，才允许使用宽泛类型。

#### Mid —— 有稳定剧情意义，但通常次于亲属/配偶/正式师承

| predicate | label | 说明 |
|---|---|---|
| `romantic_interest_in` | 单恋 | 有向，不等价于恋人 |
| `master_of` | 主仆 | 主人 → 仆从 |
| `superior_of` | 上下级 | 组织上下级 |
| `colleague_of` | 同事 | 稳定共事 |
| `business_partner_of` | 商业伙伴 | 商业合作关系 |
| `classmate_of` | 同学 | 共同就学 |
| `fellow_disciple_of` | 同门 | 同一师承/门派中的同门 |
| `ally_of` | 盟友 | 稳定联盟 |
| `enemy_of` | 敌对 | 明确敌对 |
| `rival_of` | 对手 | 竞争/对手，不必达到敌对 |
| `protector_of` | 保护 | A 对 B 有稳定保护职责/行为 |
| `benefactor_of` | 恩人 | A 对 B 有重要帮助或恩惠 |
| `companion_of` | 同行/搭档 | 稳定同行或搭档关系 |

#### Soft —— 账本可保留，默认易被压制

| predicate | label | 说明 |
|---|---|---|
| `friend_of` | 朋友 | 明确友谊 |
| `acquaintance_of` | 相识 | 认识但无更强类型 |
| `interacts_with` | 互动 | 只作为最低层 fallback，默认图可隐藏 |

罕见但重要的关系，例如：

```text
债主/债务人
医生/病人
审判者/被审判者
绑架者/被绑架者
宗教引路人
政治婚约
```

不必提前全部塞进 enum；可以由半开放 registry 学习。

### 7.2 seed 数量原则

目标不是“类型越多越好”，但**常用亲属称谓属于读者真正关心的信息，不能为了控制枚举数量而过度压缩。**

加入精确中文亲属关系后，推荐初始规模约：

```text
40～60 个常见类型
```

其中很大一部分是稳定、低歧义的 Hard kinship seeds；社交、事件类仍保持克制。

原则：

- 父亲 / 母亲、哥哥 / 弟弟 / 姐姐 / 妹妹、祖父母 / 外祖父母、伯叔姑舅姨、堂兄弟姐妹、表兄弟姐妹等高频称谓直接内置；
- `亲子 / 兄弟姐妹 / 堂表亲` 等宽泛类型只做 fallback；
- 罕见称谓不要求首版穷举，遇到后仍可由半开放 registry 学习；
- seed 扩充的目的是减少模型归一化成本并提升图的可读性，不是建立完整中文亲属本体。

### 7.3 精确关系与反向展示

关系事实应有唯一 canonical 方向，避免同一个事实因为“父亲 / 儿子”“哥哥 / 弟弟”被保存成两份。

例如：

```text
甲是乙的哥哥
乙是甲的弟弟
```

应归并为同一个 canonical fact，而不是两条独立事实。

第一版可以让 canonical predicate 表示其中一个稳定方向，例如：

```text
older_brother_of(甲, 乙)
```

前端或 Display Policy 根据方向展示对应的人类可读称谓。后续如有需要，可给 RelationDefinition 增加：

```python
forward_label: str
reverse_label: str | None
```

或等价的 role-based display 机制。

因此，**seed 精细化不等于把互为逆关系的数据存两遍。**

## 8. Evidence Resolver —— 尽量自动消化 pending

用户选择的是：

> pending 是临时状态，系统应尽量自动处理，而不是把它变成人工任务。

因此证据处理分成三层。

### 8.1 Locator：确定性定位

结果不是简单 true/false，而建议明确：

```python
locator_status: Literal[
    "located",
    "missing",
    "ambiguous",
]
```

注意：

```text
quote 没找到 / 出现多次
```

代表：

```text
无法验证
```

不代表：

```text
关系被原文否定
```

因此 locator 失败应保持 `pending`，不能直接设为 `rejected`。

### 8.2 Evidence Case 全书收集

```python
class EvidenceCase:
    case_id: str
    relation_id: str
    person_a: str
    person_b: str
    predicate: str | None
    raw_relation: str
    quote: str
    local_context: str
```

模型只判断：

```text
confirmed / rejected / pending
```

### 8.3 context window 去重

不能为了“1 次请求”把几十个 1600 字窗口机械拼成一个巨型 prompt。

先按：

```text
(chapter_id, overlapping context range)
```

合并窗口，让同一段正文中的多个关系共享 context。

再按 token/字符预算切有限 batch。

因此验收目标改为：

> **Evidence 请求数低且有上限，token 不重复搬运；不强求任何书都必须恰好 1 次请求。**

### 8.4 二次处理只针对高影响 pending

Evidence Resolver 一次批量判断后仍 pending 的关系：

- soft relation：保留内部 pending，默认不展示；
- mid relation：按展示影响决定是否进入 ExceptionCase；
- hard relation：若会明显改变默认图，可进入 High-impact Exception Resolver；
- 不允许所有 pending 再次进入“总校对”。

## 9. Canonical Fact Compiler —— occurrence 与图上事实分离

多个章节里的同一关系不是多条图边，而是一个 canonical fact 的多份 evidence occurrence。

建议：

```python
CanonicalRelationFact:
    fact_id: str
    person_a: str
    person_b: str
    predicate: str
    relation_ids: list[str]
    chapter_ids: list[int]
    evidences: list[EvidenceRef]
    confirmed_count: int
    pending_count: int
```

无向 relation person pair 强制排序。

账本 occurrence 继续保存，Canonical Fact 用于汇总和展示。

### 9.1 fact_id 必须稳定，且 fact 保留 chapter provenance

`fact_id` 不能每次编译随机生成。建议由 canonical 语义键稳定派生：

```text
(person_a, person_b, predicate, directed/canonical_direction)
→ stable fact_id
```

同一组 raw snapshots 在相同 identity / semantic decision 下重复编译，必须得到相同 `fact_id`。

Canonical Fact 不能只保存聚合计数；必须保留每个 occurrence 的章节来源，使前 N 章查询可以重新投影：

```python
occurrences: list[{
    relation_id: str,
    chapter_id: int,
    status: confirmed | pending | rejected,
    evidence_ref: ...
}]
```

`confirmed_count / pending_count` 等字段是缓存摘要，不是唯一事实来源。

## 10. Display Policy Compiler —— 解决“关系太多”，而不是让 Reconcile 删事实

这是 V2 新增的正式层。

### 10.1 默认展示规则

同一人物对允许有多个真实 relation fact，但默认标签只显示最核心的少数几个。

建议第一版：

```text
若存在 hard：
    显示全部 hard（通常数量很少）
    mid 最多再显示 1 个高价值且语义不同的
    soft 全部折叠到“更多”

若无 hard 但存在 mid：
    默认显示 1～2 个 mid
    soft 折叠

只有 soft：
    默认显示最高优先级 1 个
```

这是 UI/display 策略，不修改 ledger。

### 10.2 例子

```text
悉达多 ↔ 乔文达

账本：
- 朋友 [soft]
- 同行 [mid]
- 精神追随 / 同门（若成立）[mid]

默认图：
- 显示最高价值的 1～2 个
- “朋友”可在详情中展开
```

```text
A ↔ B

账本：
- 夫妻 [hard]
- 朋友 [soft]
- 同事 [mid]

默认图：
- 夫妻
- 必要时同事
- 朋友折叠
```

### 10.3 不再把“多标签”视作冲突

以下情况正常：

```text
夫妻 + 同事
朋友 + 师徒
盟友 + 同门
```

V2 不创建 `type_clash` 之类的通用冲突。

### 10.4 Display Policy 必须在 chapter slice 之后计算

防剧透不只影响 identity，也影响关系展示。

错误做法：

```text
先用全书 canonical facts 计算默认展示
→ 再把 chapter_ids > N 的 evidence 隐藏
```

这样仍会泄漏后文。例如第 10 章才出现 `夫妻 [hard]`，如果全书 Display Policy 已经因此把第 3 章的 `朋友 [soft]` 折叠，用户在前 N 章视图中仍然能推断后文存在更强关系。

正确顺序必须是：

```text
1. 应用 to_chapter=N 的 identity projection
2. 只取 chapter_id <= N 的 relation occurrences
3. 在该切片内重建 / 投影 canonical facts
4. 在该切片上重新计算 Display Policy
5. 再做人物出现次数过滤、势力分区和图数据输出
```

也就是说：

> **Canonical Fact 可以全书物化用于缓存，但前 N 章的可见标签与折叠规则必须基于前 N 章 occurrence 重新计算，不能复用全书默认展示结果。**

## 11. 取消固定 Final Reconcile Agent

这是本次修订相对原方案最大的变化。

### 11.1 删除的概念

不再采用：

```text
每本书
→ SuspectsGenerator
→ Final Reconcile Agent
→ Agent 自己搜索 / 读章 / 查询 cast
→ 多轮 submit
```

也不再要求：

```text
Final Reconcile 正常必须调用 1 次
```

新目标是：

```text
正常书：0 次 Final LLM
```

### 11.2 High-impact Anomaly Compiler

程序只寻找会明显污染最终关系图的异常。

第一版范围应非常保守，例如：

1. unresolved identity component 涉及高重要度人物；
2. hard/mid semantic cluster 无法归一，但会进入默认图；
3. hard relation evidence 在正常 Evidence Resolver 后仍有关键歧义；
4. 明确违反数据结构不变量的关系；
5. registry 中出现真正的 duplicate semantic definition 候选；
6. 只有在 relation type 明确定义了不可共存的结构约束时，才生成 structural conflict。

普通 pending 不属于 anomaly。

### 11.3 不自动猜“关系冲突”

以下均不能仅凭结构判定为冲突：

```text
A 爱慕 B，同时 B 爱慕 A
A 支持 B，同时 B 支持 A
同一对人物有朋友 + 师徒
同一关系在多个章节重复出现
某 occurrence rejected，另一个 occurrence confirmed
```

小说关系还会随时间变化，因此不能简单把跨章状态差异解释为矛盾。

### 11.4 Exception Resolver —— 无工具、有限输入

若确实存在 case：

```python
class ExceptionCase:
    case_id: str
    case_type: str
    related_ids: list[str]
    local_evidence: list[str]
    deterministic_facts: dict
    allowed_actions: list[str]
```

一次提供完整有限材料。

禁止：

- 搜索整本书；
- 调用工具；
- 自己扩大上下文；
- 自己创建 ID；
- 第二轮自由调查。

信息不足返回：

```text
unresolved
```

即可。

## 12. Decision 必须强类型，不能使用模糊 target_ids

原方案中统一的：

```python
ReconcileDecision(action, target_ids)
```

表达力不足。

V2 使用 discriminated union。

例如：

```python
class MergePersonsDecision:
    case_id: str
    action: Literal["merge_persons"]
    keep_id: str
    drop_ids: list[str]
    reason: str

class AddAliasDecision:
    case_id: str
    action: Literal["add_alias"]
    person_id: str
    aliases: list[str]
    reason: str

class RejectOccurrenceDecision:
    case_id: str
    action: Literal["reject_occurrence"]
    relation_ids: list[str]
    reason: str

class SuppressFactDecision:
    case_id: str
    action: Literal["suppress_fact"]
    fact_ids: list[str]
    reason: str

class ReplacePredicateDecision:
    case_id: str
    action: Literal["replace_predicate"]
    relation_ids: list[str]
    predicate: str
    reverse: bool
    reason: str

class UnresolvedDecision:
    case_id: str
    action: Literal["unresolved"]
    reason: str
```

`PatchCompiler` 只做机械转换，不进行新的语义推断。

自动 Exception Resolver **不得物理删除原始 relation occurrence**。

```text
reject_occurrence
= 将该 occurrence 标记为 rejected / suppressed，并记录 reason
= relation_id、raw_relation、quote、原始 extraction 仍保留

suppress_fact
= 只影响默认图 / canonical projection
= 不删除底层 occurrence
```

真正的人工“删除关系”仍可以通过 manual tombstone 表达，但这属于用户纠错层，不属于自动模型可执行的 destructive action。

这样可以保证：

- 自动修复可审计；
- evaluator 能看到模型曾经抽取了什么；
- 后续重构或规则变化可以重新判定；
- 不会因为一次 Exception Resolver 判断就永久丢失原始事实。

## 13. Validator 必须从旧 submit 工具中抽出来复用

当前 `submit_reconciliation` 已经实现了一部分有价值的校验：

- person ID 存在；
- merge keep/drop 不同；
- merge cycle；
- duplicate drop；
- remove relation_id 必须存在；
- relation endpoint 必须合法；
- evidence chapter 必须存在。

不要重新写一套平行逻辑。

将其抽成：

```text
ReconcileValidator / DecisionValidator
```

并增加：

- case_id 必须来自当前 batch；
- action 必须属于 case.allowed_actions；
- predicate 必须存在于 registry；
- 模型不得改写 quote；
- 模型不得引入未知 relation/person；
- merge 后不得生成 self-loop；
- 人工 edit 不得被自动 patch 覆盖。

### 13.1 Manual Override 的插入阶段与优先级必须固定

V2 中“人工优先”不能只是一句原则，必须落成明确的数据流。

#### Cast 类人工编辑

```text
manual merge / rename / alias
→ raw snapshots rebuild cast
→ replay human cast edits
→ Identity Pipeline
```

人工 merge / rename 是 Identity Pipeline 的硬约束，自动 resolver 不得拆回去或改回旧名。

#### Relation 类人工编辑

人工新增关系不写回 raw extraction，而作为独立 `human relation occurrence` 层注入；它必须在写入时已经通过服务端 validator，并引用稳定 person / predicate ID。

```text
自动 Relation / Evidence Pipeline 完成
→ 注入 human relation additions（trusted / confirmed / source=human）
→ Canonical Fact Compiler
→ Display Policy
→ 最后应用 human removal tombstones / explicit suppressions
```

人工新增关系默认不再交给 Semantic Resolver / Evidence Resolver 二次质疑；如果用户选择了新类型，应在编辑动作发生时注册为 `source=human` 的 registry definition。

优先级固定为：

```text
human explicit correction
> automatic exception patch
> normal automatic derived result
```

自动流程不得：

- reject / suppress `source=human` occurrence；
- 覆盖人工 rename / merge；
- 恢复用户已 tombstone 的自动关系；
- 用 learned predicate 替换人工选择的 predicate。

单章 rerun / 全书 rerun 后，只要对应人物仍存在，manual layer 必须 replay；若目标 ID 因 raw extraction 改变而无法唯一 remap，应进入显式 unresolved/manual-remap 状态，不能静默丢编辑。

## 14. 单章重跑：V2 先选择正确性，不做复杂增量失效

现有单章重跑只调用：

```text
enrich_ledger(rerun chapter)
→ whole-book reconcile
```

V2 不能继续这样做，因为新的 semantic cluster、identity decision 和 display facts 都是全书级产物。

### 14.1 V2 明确策略

单章重跑成功后：

```text
1. staging 中替换该章 raw extraction snapshot
2. 从所有有效 raw extraction snapshots 重建**全部工作 ledger + cast**，旧 derived ledger 不作为输入
3. replay manual cast edits / relation manual layer
4. 重新运行全书 Identity Pipeline
5. 重新运行全书 Relation / Evidence Pipeline
6. 重新构建 canonical facts；Display Policy 保留可按 chapter slice 重算的数据
7. 仅有 high-impact exception 时运行 Exception Resolver
8. 重新生成依赖结果并执行 manual tombstone / explicit suppression
9. transaction publish
```

不是重新抽取整本书，只是重新跑成本已经被压低的全书后处理。

### 14.2 为什么暂不做增量

如果 V2 后处理已经只需要个位数甚至 0～几次模型调用，那么：

```text
复杂 dependency invalidation
```

带来的工程风险大于节省的成本。

以后若《白痴》等长书证明全书后处理仍昂贵，再增加增量 cluster invalidation。

## 17. 调用次数与成本目标

### 17.1 短篇《悉达多》

不含 Chapter Agent 正文抽取。

| 阶段 | 正常目标 | 说明 |
|---|---:|---|
| Identity resolve | 0～1 | 仅 identity component 有歧义时 |
| Semantic normalize | 0～1 | 全书 semantic cluster 批量 |
| Evidence verify | 1～2 | 依 token/context window 切 batch，不强求 1 次 |
| Exception resolve | 0 | 只有高影响异常时才调用 |
| **后处理总计** | **1～4 次** | 正常不应存在 Final Agent loop |

Exception Resolver 即使触发，也必须是有限 batch，不得进入自由多轮。

### 17.2 Token 目标

《悉达多》后处理建议：

```text
正常 input tokens < 100k
架构报警线 > 150k
性能回归线 > 200k
```

重点不是追求请求数绝对最小，而是：

- 不重复携带全文；
- 不重复携带完整 registry；
- 相同语义只决策一次；
- 相同 context window 尽量复用；
- 不存在累积 Agent history。

### 17.3 长书扩展规律

模型成本主要随以下量增长：

```text
ambiguous identity components
+ ambiguous semantic clusters
+ unique evidence windows/cases
+ high-impact exception cases
```

而不是简单随：

```text
chapter_count
raw relation occurrence count
suspect count
```

线性增长。

## 19. 新增测试

### 19.1 Identity

1. A/B/C 明确专名等价形成一个 component，而不是 3 个 suspect；
2. component 一次判断返回两组人物；
3. 不同人共享泛称不得误 merge；
4. `父亲 / 先生 / 师父 / 老爷` 等高歧义称谓不得单独桥接两个 component；
5. soft evidence edge 可以进入 case，但不能改变 component 连通性；
6. manual merge/rename 优先；
7. merge 后关系 endpoint、event、override 全部正确 remap；
8. wrong merge fixture 必须为 0。

### 19.2 Semantic clustering

1. 20 条相同 descriptor → 1 cluster；
2. 跨 12 章相同 descriptor → 1 cluster；
3. 同 label 不同 definition 不得 exact 合并；
4. directed/undirected 不得合并；
5. role 不等价不得合并；
6. candidate retrieval 必须包含真正已有 predicate 的测试。

### 19.3 Evidence

1. quote missing → pending，不是 rejected；
2. quote ambiguous → pending；
3. 同一 context window 中多个 relation 共用正文片段；
4. provider failure → 保留 pending；
5. soft pending 不进入 ExceptionCase；
6. hard pending 可按影响进入 ExceptionCase。

### 19.4 Display Policy

1. `朋友 + 师徒` → 账本两条都在，默认只显示师徒；
2. `夫妻 + 同事 + 朋友` → 夫妻优先，朋友折叠；
3. 两个 hard 可共存；
4. 只有 soft 时仍显示最核心一个；
5. Display Policy 不修改 ledger。

### 19.5 Exception Resolver

1. 没有 high-impact case → 0 模型调用；
2. 20 普通 pending → 0 ExceptionCase；
3. batch 不携带上一批聊天历史；
4. 模型引用未知 ID → validator reject；
5. unauthorized action → reject；
6. unresolved → 不自动发起第二轮调查；
7. `reject_occurrence` 后 raw relation / quote / relation_id 仍可审计；
8. 自动 resolver 不得 reject / suppress `source=human` 的关系。

### 19.6 单章重跑

1. 只重新抽取目标章；
2. 但全部有效 raw snapshots 都重新生成 working ledgers / cast，再跑全书 postprocess；
3. 不读取上一代 postprocessed ledger 作为新一代输入；
4. manual edit 保留；
5. 自动 patch 不叠加；
6. staging 失败不污染 live；
7. 旧章因新 identity merge 需要 remap 时结果正确更新。

### 19.7 防剧透 chapter slice

1. 第 10 章才确认 A=B，`to_chapter=5` 时仍保持两个节点；
2. 第 9 章才出现真实姓名，`to_chapter=3` 不显示后期真实名 / alias；
3. 第 10 章新增 `夫妻[hard]`，不得让 `to_chapter=5` 的 `朋友[soft]` 因全书 Display Policy 被提前折叠；
4. chapter slice 的人物数、关系数、appearance_count 只由切片内数据决定；
5. 全书图与前 N 章图共享 raw facts，但不能共享已经计算好的全书默认展示结果。

### 19.8 幂等与 generation

1. 固定 raw snapshots 连跑 V2 两次，registry definitions 完全一致；
2. 无真实 registry 变化时 version 不增长；
3. 同一 canonical semantic key 生成相同 `fact_id`；
4. 第二次运行不得因为上一代 derived ledger 存在而改变 semantic / evidence 结果；
5. generation 失败后 live 仍保持上一代完整结果。

### 19.9 Manual Override

1. manual cast rename / merge 在 Identity Pipeline 中是硬约束；
2. manual relation addition 以 `source=human` 进入 canonical facts；
3. manual removal tombstone 在 rerun 后仍生效；
4. 自动 Exception Resolver 不得覆盖任何人工关系编辑；
5. 人物 ID 变化但可以唯一 remap 时人工编辑自动迁移；无法唯一 remap 时显式报 unresolved，不静默丢失。

## 23. 性能与产品验收定义

- [ ] 不存在 Final Reconcile tool-calling loop；

## 25. 最终结论

旧系统的问题不是“Reconcile Agent 不够聪明”，而是它承担了不该由 Agent 承担的职责。

ZhiYing 真正需要的是：

```text
自动认人
+ 尽量完整地记录关系
+ 全书级语义去重
+ 自动证据验证
+ 强弱关系展示收敛
+ 极少量高影响异常修复
```

而不是：

```text
抽取一次
→ 最后再让另一个 Agent 调查整本书并重做判断
```

因此 V2 的最终架构原则是：

> **账本尽量完整，图面主动收敛；自动解决身份问题；普通不确定性在所属阶段解决；只有真正会污染最终图的少量异常才进入一次性 Exception Resolver。**

如果这套架构实现正确，《悉达多》这种规模的作品不应该再需要几十次后处理模型调用，更不应该消耗百万级重复 Token。
