# 验收场景（Gherkin）

产品事实源为 [PRD](../PRD.md)。这些 Gherkin 文件把已确认规则展开为可执行规格的输入，不替代 PRD；新产品决定须先写入 PRD，再同步场景。实现方案见 [DESIGN](../DESIGN.md)。

目前提供 `.feature` 文本，尚未绑定 Kotlin 步骤定义、测试适配器与运行器，因此不是已经通过的自动化验收。使用英文 Gherkin 关键字和中文业务描述；`@confirmed` 表示规则已确认。每个场景有稳定编号，场景大纲的每一行 Examples 都是独立验收实例。

## 如何接入测试

- **流程与领域验收**：模型适配器使用可控替身，提供明确的身份、关系与补查结果；Given 必须建立真实状态，When 调用实际应用用例，Then 读取结果、持久化状态或请求记录。不能让步骤仅返回输入表格或模型自述后就算通过。
- **前端验收**：聚焦、更多、图例、样式与导出接入保留的前端。领域测试通过不能代替用户可见行为的验证；PNG 要检查实际导出内容，JSON 要解析并验证引用完整性。
- **模型质量评测**：真实模型能否从原文正确认人、分类和判断，使用保留的评测集另行验证。这里的合成微型原文用于描述规则，不是新的质量基准；替身下通过不能证明抽取准确率。
- **补查预算**：`REVIEW_04` 的 2 次是测试配置，用来证明上限有效，不是已确定的生产默认值。工程实施时设置请求数、条数、输入长度与耗时上限，不能无界循环。
- **不写虚假通过步骤**：步骤未实现时应保持未定义或明确失败，不能用空步骤把文档变成绿色报告。接入运行器后执行场景大纲的全部 Examples。

严格防剧透、加强证据模式、人工纠错不属于验收范围；评测分数门槛待定（PRD §9）。运行、发布与恢复的工程性质可另设集成测试，但不能在产品发布策略未确认时把某种行为暗中固定下来。

绑定运行器时从 `FLOW_01–03` 入手；尚待确认的产品行为见 PRD §9，确认后先更新 PRD 再补场景。

## 测试约定

越接近真实使用的测试越重要，在精不在多。本项目以模型判断为主，纯函数单元测试价值低，不追求单测数量与覆盖率。

| 测试 | 验证内容 |
|---|---|
| Gherkin 验收（主力） | 本目录的场景，从输入到用户可见结果；模型用可控替身 |
| 行为 / 集成测试 | 走真实 HTTP 与真实 SQLite：事务与回滚、重跑、发布一致性、取消、接口与进度契约 |
| 架构检查 | 领域不依赖框架；包无循环 |
| 真实模型评测 | 另行专项（DESIGN §7）；保留抽取输入输出、判断结果、最终图与运行用量 |

- 只有规则复杂且容易写错的领域逻辑（身份合并、方向归一、软兜底时机）才值得单独测试
- 不给 DTO 字段写无意义断言；步骤未实现时保持未定义或失败，不写空步骤
