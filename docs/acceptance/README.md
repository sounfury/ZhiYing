# Kotlin 重构验收场景

产品事实源为 [PRD v0.9](../PRD.md)。这些 Gherkin 文件把已确认规则展开为可执行规格的输入，不替代 PRD；新产品决定须先写入 PRD，再同步场景。实现方案见 [Kotlin 重构梳理](../design/kotlin-domain-and-layers.md)。

目前提供 `.feature` 文本，尚未绑定 Kotlin 步骤定义、测试适配器与运行器，因此不是已经通过的自动化验收。使用英文 Gherkin 关键字和中文业务描述；`@confirmed` 表示规则已确认，不表示已实现或已选为首批故事。每个场景有稳定编号，场景大纲的每一行 Examples 都是独立验收实例。

## 如何接入测试

- **流程与领域验收**：模型适配器使用可控替身，提供明确的身份、关系与补查结果；Given 必须建立真实状态，When 调用实际应用用例，Then 读取结果、持久化状态或请求记录。不能让步骤仅返回输入表格或模型自述后就算通过。
- **前端验收**：聚焦、更多、图例、样式与导出接入保留的前端。领域测试通过不能代替用户可见行为的验证；PNG 要检查实际导出内容，JSON 要解析并验证引用完整性。
- **模型质量评测**：真实模型能否从原文正确认人、分类和判断，使用保留的评测集另行验证。这里的合成微型原文用于描述规则，不是新的质量基准；替身下通过不能证明抽取准确率。
- **补查预算**：`REVIEW_04` 的 2 次是测试配置，用来证明上限有效，不是已确定的生产默认值。工程实施时设置请求数、条数、输入长度与耗时上限，不能无界循环。
- **不写虚假通过步骤**：步骤未实现时应保持未定义或明确失败，不能用空步骤把文档变成绿色报告。接入运行器后执行场景大纲的全部 Examples。

防剧透、加强证据模式、人工纠错、旧书迁移不属于本期验收。不以旧评测分数或此前评论中的 90 分作为门禁。运行、发布与恢复的工程性质可另设集成测试，但不能在产品发布策略未确认时把某种行为暗中固定下来。

## 现在能否开始重构

**可以开始 Kotlin 骨架、核心领域规则与成功路径的垂直闭环；不宜现在就承诺全部替换旧后端并上线。** 现有决定足以支撑第一批代码，无需再次确认身份规则、软兜底、证据模式或是否人工审核。

建议首批选择：EPUB → 章分析适配器 → 人物身份 / 关系与证据规则 → 汇总图 API → 现有前端展示。以 `FLOW_01–03` 为入口，配套选择身份、关系与证据文件中的场景。先使用可控模型结果验证规则，再接真实模型与既有评测材料；这是建议开发顺序。首批交付已确认包含团体分区与有向关系，不能仅完成基本图谱就宣称首批交付完成；还需覆盖团体文件及方向场景。

以下取舍在进入对应故事前确认，不阻塞无关领域规则与成功路径：

| 待确认事项 | 需要决定的具体行为 | 影响 |
|---|---|---|
| 失败章节与结果发布 | 部分章节失败、自动重试结束后，是否允许用户看到成功章节的新结果；重跑失败时是否保留上一版，界面如何告知缺章 | 任务状态、发布与重跑的验收，不能把“关系未决不阻塞”套用为“整章失败也自动发布” |
| 关系与事件的具体边界 | “精神引导、技艺指导、长期共同生活、一次援助”等文本，何时支持硬 / 中类型，何时仅保留事件或走有依据的软兜底 | 类型库、抽取提示与真实模型样例；本次没有替用户确定这些答案 |

量化质量目标和评测机制已明确交给专项，不重复要求本轮定分数。技术框架、模块组织、步骤定义与存储实现可在现有分层方案下继续细化；生产补查预算可以先作为可配置工程参数，不必让用户拍一个没有实验依据的数字。

确认以上问题后，先更新 PRD 和相应场景，再实现受影响的故事。验收文档不放在临时 `docs/design/` 内，后续作为 PRD 的行为规格持续维护；完成重构时应清理临时设计稿，而非删除仍用于验收的场景。
